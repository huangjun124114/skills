# 检验体系（verification-gates）

**每一轮结束都要跑全部六道闸**，不是只在最后一轮跑。每道闸不通过就停下来排查，不带着问题进入下一轮。

## 闸门 1　内容守恒

```
missing = expected_keep − actual_files
```
必须为 **0**。任何"该留却不见了"都是缺陷，不是清理成果。

`expected_keep` 的构造：本轮策略算出的"应移除集合"之外，上一轮归档区的全部文件。

## 闸门 2　去重

归档区内部 md5 重复必须为 **0 组**。
写入时按 md5 索引去重即可保证；若出现重复，说明幂等逻辑失效。

## 闸门 3　上下限

- 无文件夹超过约定上限（除非用户明确特批，需记录）
- 无文件夹少于 3 张
- 无空文件夹

空文件夹处理：`os.rmdir` 会被沙箱拦截，改用 `shutil.move` 移入隔离区。

## 闸门 4　备份闸门（销毁前置条件）

**两个条件必须同时满足**才允许删除源文件：

1. 该文件的 md5 **已存在于归档区**（即确实已被整理）
2. 备份区中存在 md5 **完全一致**的镜像文件

任何一条不满足 → 跳过，记入 `unverified` 清单，绝不删除。
容忍度：**0 个不可校验**。

## 闸门 5　隔离区对账

```
隔离区唯一 md5 数  ==  预期移除数
```

**不一致的常见原因**：脚本重复执行，产生同名不同后缀的冗余副本。
实测一次：116 个内容产生了 292 个文件（176 个冗余），原因是重名时自动追加 `_1`/`_2` 后缀。
处理：按 md5 去重，每个内容保留一份后再对账。

## 闸门 6　ctime 审计

`shutil.copy2` 保留 mtime/atime，但**ctime 是新的**。按 ctime 分组能看出"哪批文件是什么时候进来的"。

```
08-28 20:16 : 1,523 张   ← 第一轮拷贝
08-28 22:37 :   627 张   ← 上限放宽补充
08-29 10:05 :   361 张   ← 第二轮（上限 60）
08-29 10:19 :   142 张   ← 上限放宽到 80
08-29 10:23 :     8 张   ← ★ 不在任何清单里
```

**实战收益**：靠这道闸发现 8 张来源不明的文件——同一时刻、来自单一源子文件夹一次性写入，项目没有任何脚本会这么写。经三处字节比对确认无害后由用户处置。没有这道审计，相册里会永久躺着来源不明的内容。

**对账模板**

```python
expected_remove = 策略算出
expected_keep   = scores 全集 − expected_remove
actual          = 归档区当前文件集合

missing = expected_keep − actual      # 必须 0
extra   = actual − expected_keep      # 人工特批保留的，逐条说明
assert len(quarantine_unique_md5) == len(expected_remove)
assert not (archive_md5 & quarantine_md5)
```

## 补充：文件数变化 ≠ 内容丢失

迁移后总数可能变化，原因是原始数据中跨文件夹的重复副本被清理。判定标准是 **md5 内容守恒**（备份唯一内容 ⊆ 归档区唯一内容），**不是数量相等**。
